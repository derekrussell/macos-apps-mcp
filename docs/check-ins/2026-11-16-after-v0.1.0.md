## How work is tracked

From this check-in, the project mirrors a plan/record split:

- `docs/build-roadmap.md` is the plan and the record: numbered milestones
  (M1, M2, …), each with a "Done when" line, a status, and notes on why things
  were built as they were. Changes made at a check-in are marked in place.
- `docs/architecture-decisions.md` records lasting decisions and their reasons.
- `docs/check-ins/` holds one note per check-in.
- On GitHub, each roadmap milestone is a Milestone, broken into small issues
  just before it starts — each finishable on its own and usually one pull
  request. Open questions are issues labelled `question`, each saying when it
  will be decided. `housekeeping` marks small chores; `candidate` marks ideas
  driven by use that belong to no milestone yet. A GitHub Project board gives
  the overview.
- Nothing is listed in both the docs and GitHub, so they cannot drift apart.
- Work stays inside the current milestone.

Milestones are now named by deliverable (M1, M2, …) rather than by version.
Which release ships each milestone is decided when it is done. The old v0.2.0
and v0.3.0 milestones are closed once their issues have moved, and the two
README milestone badges are removed.

## Developments

- **mcp 2.0 is stable** (2.3.0, 2 October 2026), targeting the 2026-07-28 MCP
  specification, which removes the opening handshake. Servers and clients on
  different specification revisions may not work together. mcp 1.x still
  receives security fixes, so the `<2.0` pin stays; the upgrade is M3, and it
  starts by confirming Claude Desktop works with a 2.x server.
- **macOS 27:** no documented changes to Mail, Reminders or Notes scripting
  were found. A reported macOS 26.1 change (Mail wrapping message IDs in
  `< >`) does not affect this server: smoke run 15, on macOS 27.0.1, passed
  every Mail step, including get → move → delete by message ID.
- **Claude Desktop runs two copies of one server entry.** Observed on
  14 November 2026: two server processes from one config entry, started
  16 minutes apart. Each keeps its own reminder index and refreshes it
  independently, so the two compete for Reminders. This is the likely cause
  of smoke run 15's failed `reminder_update` (see #18). Why the client starts
  two copies is checked at the start of M3.

## Decisions

Kept, with nothing changed: AppleScript only, Apple's built-in apps only;
the roadmap is driven by real use; discoverability (#7–#10) stays deferred;
no mailbox-delete tool (Mail cannot script it); the reminder search index is
built in the background and updated in place by edits; mcp stays below 2.0
until M3.

**New — tool presets.** Previously every tool was available to every client
session. An AI client that reads email can be steered by hidden instructions
inside an email (prompt injection), so the server itself now limits which
tools a session gets — a rule enforced by the server can't be talked around,
and doesn't depend on client settings. One setting, `MACOS_APPS_PRESET`,
picks a preset:

| Preset | Tools |
|---|---|
| `read-only` (default) | The 13 read tools across all three apps |
| `triage` | Mail reads, plus `mail_move` limited to listed destinations |
| `structure` | `mail_list_mailboxes`, `mail_create_mailbox`, `mail_rename_mailbox` |
| `notes-reminders` | All Notes and Reminders tools, deletes included; no Mail |
| `full` | Everything (development and smoke tests) |

Every preset also includes a new `server_status` tool reporting the active
preset, its tools and its move destinations. The details:

- Switched-off tools are left out of `list_tools` and refused in `call_tool`.
- A missing setting means `read-only`. That is a behaviour change: an
  existing configuration with no setting loses its write tools until a preset
  is chosen. An unrecognised value stops the server at start-up with a message
  naming the valid presets. Case and stray spaces are ignored.
- `mail_move` can reach any mailbox, Trash and Junk included, so leaving out
  `mail_delete` alone would not stop trashing. In `triage`, moves are allowed
  only into the branches listed in `MACOS_APPS_MOVE_TO` (separated by `;`).
  An entry allows that mailbox and everything beneath it, matched on whole
  path segments and exact case. An empty list allows no moves.
- Tools that change existing content (`notes_update`, `reminder_update`,
  `reminder_complete`) are treated like deletes and kept out of every preset
  that reads mail.
- `mail_delete` remains, in `full` only.
- Every tool carries a `readOnlyHint` or `destructiveHint` annotation. These
  are hints to clients, not enforcement.
- The reminder index is warmed at start-up only when the preset includes
  Reminders tools.
- All policy lives in a new `tools/_presets.py`, with explicit tool lists per
  preset. A new tool is therefore in no preset except `full` until it is
  added deliberately.
- Considered and dropped: sending the preset in the server's `instructions`
  text. The 2026-07-28 specification removes the handshake that carries it,
  and `server_status` already does the job.

**New — the Reminders index holds open reminders only.** Each index rebuild
currently reads every reminder in full and drops the completed ones in
Python. Smoke run 15 counted 1,582 completed against 15 open, so about 99% of
each rebuild reads history that the default views never show. Reminders'
AppleScript has no cheap "open only" filter (`whose completed is false` costs
one round trip per reminder), which is why everything is read. M2 investigates
reading only the completion flags in bulk and then full details for open
reminders only. Completed history becomes opt-in, read on demand within a
time budget. This means `reminder_completed_stats` is no longer served
instantly from the index — a reversal of a #24 design point.
